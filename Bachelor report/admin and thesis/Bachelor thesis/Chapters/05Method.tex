The system follows a client-server architecture. The backend is written in Go and runs inside a Docker container that exposes a REST API. Swagger is used for API documentation. The frontend is built with React and TypeScript and retrieves the data it needs through API calls to the backend.

\subsection{Backend and Data Flow}

The backend infrastructure and test database were provided by the customer, pre-populated with test data since actual AIS anomaly data is confidential. The team's main contribution to the backend was a master query endpoint. This endpoint accepts all filter parameters (anomaly type, mmsi, and time range.) and returns only the matching data. Instead of getting all the anomaly groups and filtering on the frontend, all variables get sent to the backend which queries the data again. This was done since keeping old data and filtering client-side was slow and inefficient.

\subsection{Frontend Architecture}

The frontend architecture was designed to follow a client-driven data flow, where data is to be retrieved from the docker backend, through API calls via the react Axios library. Data requested through the REST API backend, section \ref{sec: rest api}. Is then saved as geoJSON in the frontend. geoJSON is to then serve as anomaly-group data points in the system. Data retrieval leads to map creation through Maplibre, which functions as the map visualized on the application. Maplibre is the base map visualization layer of the application, serving as the map in which data points are overlaid. Visualization on maplibre, is done through the deck.gl library. section \ref{sec:deckgl} Deck.gl allows different visualization methods to be implemented through the deck.gl API, deck.gl serves as the main visualization component, which uses the geoJSON data to visualize anomalies. 

The frontend itself is structured as a collection of React components, that are made to interact through, use of state and an event driven design. State is used for rerendering layers, and change of state itself is implemented to change through user interface and API calls. 


All core parts of the interface, such as maplibre, are wrapped as components to be rendered by the react tree. Components acquire data from modules holding functions for data initialization, change of visualization method, with click interaction and searching function implemented. 

The frontend is designed to allow for user interaction, through a user interface of react components. The design is allowed for end users to be able to interact with specific anomaly groups, through click events, allowing the user to observe anomaly groups visualized through different implementations such as a heatmap or a clustered scatterplot. Interaction is designed to allow for the user to retrieve information on anomaly groups through click events on clusters, creating a component with information and allowing further interaction. 



\subsubsection{Frontend Data Flow}


The frontend data flow through REST API calls was chosen because it allows for large data sets to be retrieved and saved using react state, allowing for the data to be sent through the application where needed for visualization and component purposes.  


\paragraph{Data Retrieval and Filtering Strategy}
When specific or filtered data is required, the frontend issues additional REST API requests to the backend, rather than performing full dataset filtering locally. The frontend state is then updated with the returned subset of data.

\subsubsection{REST Communication with Axios}
REST communication between frontend and backend was handled using axios. This was chosen to enable asynchronous HTTP requests, without blocking the user interface, while allowing for dynamic updates to the dataset where needed, such as querying for specific anomaly types or date range. Axios allows for the application to be designed to update in real time, where a API call returns a promise of the data requested, which in turn allows the application to update after the data is successfully retrieved, leading to real time updating of the user interface. This in turn leads to a more responsive user interface for end users.

\subsection{Clustering}


As mentioned in Section \ref{sec:supercluster}, Supercluster.js is used for calculating clusters based on zoom level and the current map bounds. Supercluster calculates clusters based on the base dataset acquired from the API, calculating all clusters on application load. Map interactions such as zooming and dragging result in clusters being retrieved for the current zoom level and map bounds. The clustering data itself is used with deck.gl,Section \ref{sec:deckgl}. Visualization through deck.gl is accomplished through creating a custom layer, consisting of a label-layer, whose purpose is to be a point counter for the amount of anomalies inside the cluster, this is put over, a scatterplot-layer. section \ref{sec:scattermap}, which combines to create the clustering layer.This layer is re-rendered whenever the clustering output changes due to updates in zoom level or map bounds. Furthermore does clustering visualization have dynamics sizing based on amount of anomalies inside a cluster, leading to clusters being scaled proportional to their anomaly count.

\subsection{Anomaly Group Layer}
The anomaly group layer, is a visualization layer that gives a detailed representation of a single anomaly group, section \ref{sec:anomalies and anomaly groups}. The anomaly group visualization layer is created through a custom deck.gl layer. This layer consists of a signal strength layer, using data from the individual anomalies inside the group, that are connected to a satellite or base station with a signal strength number value, normalized between 0 and 1. The signal strength layer adds lines from the source anomaly, to the receiving base station and or satellite, indicating the strength of received AIS-message.
