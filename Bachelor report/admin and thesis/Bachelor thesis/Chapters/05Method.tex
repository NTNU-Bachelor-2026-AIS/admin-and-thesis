This section describes how the project was organized, including the development methodology, team structure, meeting routines, communication, and task management tools used throughout the project.

\subsection{Scrum Framework}
\label{sec:dev_methodology}

The Scrum framework, described in Section \ref{sec:scrum_framework_theory}, was adopted to structure the development process. The framework was introduced by the supervising lecturer, who provided pre-filled sprint templates and documentation to support its application for groups. Scrum was chosen for its suitability with iterative development and its continuous feedback loop, which allows for early changes in direction. This lowered the time investment of adopting the system and methodology, while ensuring that sprint artefacts such as the backlog and retrospectives were maintained throughout the project. 

% TODO: Need to add more info about retrospectives. How long each sprint was 1-2 weeks
Scrum was also well suited given the project's biweekly meetings with the supervisor and the customer at the NCA. Each sprint would ensure that further development in the project could be presented and discussed, allowing scope adjustments to be made based on the feedback, which would help if technical issues were to occur, such as limitations or issues with the AIS dataset or uncertainty around feasibility or scope for specific visualisation features. The iterative structure then allows focus on the backlog until discussions about scope or features with the customer at the NCA rather than following a fixed plan. The project's internal sprint structure was organized into weekly sprints, which followed issues created on Github related to that weeks iteration. At the end of each sprint, a short retrospective meeting was conducted to evaluate the progress of the group, planning what to focus on the next group, which lead to what to prioritize from the backlog if any issues were not completed during the sprint. This was then used to plan the following sprint. 

\subsection{Daily Stand-Ups}


Daily stand-up meetings were established as a core part of the sprint work flow, in line with the Scrum practices described in Section \ref{sec:scrum_framework_theory}. The primary purpose of the stand-ups is to maintain accountability between team members and to further facilitate collaborative problem-solving between team members when problems blocking further development arise. 

In a two-person team, the risk of one member being stuck on a problem without the other member being aware is likely. Daily meeting allowed such issues to be discussed early, preventing them from blocking further project development. They can also be utilized as a daily forced break for the team. Sustained work without regular breaks does not equated to consistent productivity. While also being a way to quickly discuss a problem for further collaborative work after the stand-up meeting. While the daily stand up was followed once daily, there were multiple days where daily meetings while walking to facilitate a break were done, while discussing the project further.

\subsection{Frontend Architecture}

The frontend architecture follows a client-driven data flow where data is retrieved from the backend through REST API calls using Axios (Section~\ref{sec: rest api}). The received data is stored in React state as a geoJSON FeatureCollection, which is passed to individual Deck.gl layers responsible for rendering the visualisations. This is done after a map instance is created through a map container class, using maplibre. deck.gl is subsequently used for rendering data points overlaid visually on the map. Interactivity is handled through React components, where state changes control filtering and updating of the rendered layers. Individual Deck.gl layers also implement click event handlers, which update application state and trigger the rendering of additional information components or different visualization layers (~\ref{sec:deckgl}).

\subsection{Frontend component structure}


The frontend is implemented as a single-page application, centered around the main map. The interface is structured as a set of components, with the map being central to the page. Different components are put over the map that allow for filtering, anomaly search and context sensitive information displays for anomalies.  


The application maintains shared state of the currently loaded dataset, being sent down to components that need it. Active filters are maintained with a state, where any changed in the current filter is observed by other components, and will trigger visualization change. 


The applications uses no routing, as it is a single page application, with all components dynamically handled and updated based on application state. 

\subsubsection{REST Communication with Axios}
%Needs to be broken up sentences are too long

REST communication between frontend and backend was handled using Axios. This was chosen to enable asynchronous HTTP requests, without blocking the user interface, while allowing for dynamic updates to the dataset where needed, such as querying for specific anomaly types or date range. Axios allows for the application to be designed to update in real time, where an API call returns a promise of the data requested, which in turn allows the application to update after the data is successfully retrieved, allowing real-time updating of the user interface. This in turn leads to a more responsive user interface for end users\parencite{geeksforgeeks_axios}.

\section{Backend and Data Flow}
\label{sec:backend_and_data_flow_method}
% Section intro with bridge to System Architecture

% This is actual content might need some more content

The backend infrastructure and test database were provided by the customer, pre-populated with test data since actual AIS anomaly data is confidential. The team's main contribution to the backend was a master query endpoint. This endpoint accepts all filter parameters (anomaly type, mmsi, and time range.) and returns only the matching data. Instead of getting all the anomaly groups and filtering on the frontend, all variables get sent to the backend which queries the data again. This was done since keeping old data and filtering client-side was slow and inefficient.

The anomaly set is saved as a featureCollection in geoJSON, with a featureCollection being the entire set of geographic objects. The anomaly data is built up such that all anomaly groups are part of a collection.

While individual anomaly groups also are collections that have individual features inside, a feature being an individual anomaly inside a group, relating to a single ship's anomaly. 

When a request is made, the backend first retrieves the relevant anomaly groups, based on the frontend request, returning a geoJSON FeatureCollection.

\subsection{Clustering}
\label{sec:clustering_method}

% Some sentences need to be split for a cleaner structure.
Clustering was implemented based on customer request, as a way to reduce visual clutter and improve human readability when visualizing large datasets. It follows general clustering theory from (Section~\ref{sec:clustering}). As mentioned in Section \ref{sec:supercluster}, Supercluster.js is used for calculating clusters based on zoom level and the current map bounds. Supercluster calculates clusters based on the base dataset acquired from the API. The clustering behavior is controlled through a fixed radius parameter, where anomalies close together in the predefined radius are put in a cluster. Map interactions such as zooming and dragging result in clusters being retrieved for the current zoom level and map bounds. Supercluster itself was chosen for its ease of use with geoJSON, while being designed for fast calculations, through the use of hierarchical greedy clustering, while reusing previous calculations (Section~\ref{sec:supercluster}). 

The clustering data itself is used with deck.gl,Section \ref{sec:deckgl}. Visualization through deck.gl is accomplished through creating a custom layer, consisting of a label-layer, whose purpose is to be a point counter for the amount of anomalies inside the cluster, this is put over, a scatterplot-layer. section \ref{sec:scattermap}, which combines to create the clustering layer.This layer is re-rendered whenever the clustering output changes due to updates in zoom level or map bounds. Furthermore does clustering visualization have dynamic sizing based on amount of anomalies inside a cluster, leading to clusters being scaled proportional to their anomaly count.

\subsection{Heat Map}
\label{sec:Heat_Map_method}

A heat map layer was implemented for visualization of the full dataset \ref{sec:heatmap}. Heat map visualization is done through deck.gl HeatMapLayer. Each data point contributes equally to the weighted visualization, where radius based proximity is used to calculate the color shown, 
correlating to density of points. 

The visual representation of density is accomplished through densities being given weight, which then is translated to a color scale. Lower densities correlate to a yellow color while higher densities show a redder color. 

The heatmap updates when the zoom level or view changes, leading to recalculation of density, as points are further apart on zoom-in.

\section{Filter and Interaction}

The filtering and interaction system builds on the visualization layer described in Section~\ref{sec:visualization_implementation}. This section will explain the implemented interaction and filtering systems.  

\subsection{Filter System}

The filter system was scoped early in the project. Group-level filtering was chosen over per-anomaly filtering, because filtering per-anomaly would include more data fields such as source ID, signal strength and more which was concluded to be too computationally expensive for interactive use on a large database. Since the main scope of the project was focused on anomaly groups, this scope made sure that the filter would be focused on performance while aligning with the visualisation goals of the project. For this four filterable fields were selected: ID, MMSI, anomaly type and last activity. These were chosen to support the operators work-flows since they were the information most likely to be investigated in practise. Things such as isolating anomalies by time period, type, or MMSI. Then using that filtered data to find specific areas of elevated anomaly density.

\subsection{Temporal Filtering}

A simple date-time range selector was selected for temporal filtering. The design goal is to let operators restrict the visualisation to a chosen time period and then use other tools to further identify special factors of points in that period. However it was still focused on being within the scope while being feasible to develop so it focused on simplicity.

\subsection{Satellite Implementation}

Satellite connections was implemented as a layer that would only be visualised when a point is clicked to follow the project scope and make sure that complexity stayed low. This decision made sure that operators could not clutter the screen with satellites and allows them to see the points and connections easily.

\subsection{Interactive Features}

The filtering controls are designed for simple, interactive operation. A pop-up calendar component was implemented for date selection, and a drop-down listing the available types was implemented for anomaly type selection. A third component was for inputting numbers which was implemented for mmsi selection. These standard interfaces were chosen to keep the filtering workflow familiar to other systems while also allowing operators without prior training to use the prototype.

Testing of the system was conducted through manual testing of the application, based on the testing theory described in (section~\ref{sec:testing_theory} and (section~\ref{sec:manual_testing_theory}).

\subsection{Backend API Testing}

As the backend was primarily created by the customer, leading to actual tests not being created by the group. However manual testing of results were done through a swagger api, to check the result of request, while also being tested in the application itself.

Additional testing was performed on the backend, through logging of retrieved data on the console in the browser, observing correctness by analysing the data that was received. 

The swagger API allowed for testing of endpoints, as long as the backend was running. This was done through giving different variables such as an anomaly id, then observing the API response 


\subsection{Frontend Testing}

Frontend testing was done manually through direct interaction with the application. This included testing the core functionality.

The components were tested to ensure that correct information is displayed, this in turn tested with console logging to see what information is being accessed, while also testing the swagger API to see if the data at that specific endpoint is what is shown in the components. 

Testing of specific methods in the code was done through console logging, to find errors and to see if correct methods were called. In addition to this testing of all filtering and search functionality was done through the application itself, while ensuring that correct data was observed to be returned. 

\subsection{Performance Observation Methodology}

Performance was evaluated through manual observation of the application during use. No automated performance testing was implemented. The system was tested using datasets ranging from 10,000 anomalies to over 100,000 anomaly groups. The focus of any performance testing was to ensure that the application was responsive for end users, and that rendering behaviour was exempt from major performance issues. 

To ensure performance of the system, certain implementations were made, such as reducing the frequency of recalculations of clusters on drag and zoom operations, and using virtualization in the sidebar such that the entire data set was not rendered at all times in the list.

\section{User Feedback}
\label{sec:user_feedback}
% Section intro with bridge

User feedback was gathered primarily through the biweekly customer meetings as described in \ref{sec: meeting structure}. These were used to gain feedback on design mostly using the customers opinion to further reduce complexity and scope while making sure the product was developed how they wanted.

The Feedback was used to iteratively change the development with the project, where features were scrapped and added as requests during the project through communication. This was done to ensure wasted work on unwanted features were minimized, while allowing for changes to be made early in development. 

At the end of the project, a video of the application, with questions to employees at the NCA, was sent to the customer representative. This allowed to get feedback from actual operators currently using the NCA's internal system, to see if the implemented functionality would bring value to them.
